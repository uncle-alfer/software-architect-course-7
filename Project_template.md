# Задание 1. Исследование моделей и инфраструктуры для RAG-бота

## Определения

* **Локальные (self-hosted) модели** - любые модели, которые мы **разворачиваем и обслуживаем сами**:
  - on-premises сервер(а) в ДЦ компании или приватном сегменте;
  - рабочая станция/ноутбук сотрудника (x86/ARM, с/без GPU);
  - приватный IaaS/VM/Kubernetes в нашем аккаунте облака, **если инференс выполняется на наших инстансах**, а не через сторонний LLM-API.
  Критерий: данные **не покидают наш периметр** к стороннему провайдеру LLM, а вычисления - под нашим контролем.
* **Облачные (managed-API) модели** - генерация или эмбеддинги вызываются у внешнего провайдера как сервис (OpenAI, YandexGPT и т.п.). Данные запроса уходят за периметр по API (с учётом договоров/DPA/политик).
* **Гибрид** - хранение/ретрив и/или эмбеддинги локально (self-hosted), а генерация - через облачный API (или наоборот).

---

## 1. LLM: локальные (Hugging Face) vs облачные (OpenAI / YandexGPT)

### Качество ответов

* **Локальные 7-8B (Llama 3.1-8B-Instruct, Mistral-7B-Instruct)**: уверенно закрывают типичный RAG при корректном ретриве/реранке. Для сложных рассуждений и «агентных» задач уступают облачным флагманам.
* **OpenAI**: текущий флагман - GPT-5 (новый дефолт в ChatGPT/моделях API), сфокусирован на коде, агентности и «умном» роутинге/reasoning. Высокое качество и стабильность для прод-кейсов.
* **YandexGPT**: актуальная линейка YandexGPT 5 / Pro 5.1 (RC) в составе Yandex AI Studio; сильные русскоязычные сценарии. Важно учитывать региональное хранение/юрисдикцию.

### Скорость работы

* **Локально с GPU 12-16 ГБ VRAM** (INT4/INT8): интерактивно (низкая латентность), особенно для 8B-моделей. Без GPU - возможно, но ощутимо медленнее.
* **Облако**: высокая скорость и масштабирование «из коробки», но добавляется сетевая задержка.

### Стоимость владения и использования

* **Локально**: разовый CapEx (GPU) + OpEx на поддержку. Экономно при стабильном/высоком трафике и строгой приватности.
* **Облако**: чистый OpEx и «платишь по мере использования». Выгодно на старте и при непредсказуемой нагрузке.

### Удобство и простота развёртывания

* **Облако**: самый быстрый старт (SDK, готовые клиенты, мониторинг).
* **Локально**: больше сборки (квантовки, контейнеры, драйверы), но полный контроль.

**Вывод по LLM**: для кейса с чувствительными данными оптимален гибрид - локальное развёртывание 8B-модели (INT4) + облачный fallback для «тяжёлых» запросов. Если политика требует «без облака» - остаёмся полностью локально.

## 2. Эмбеддинги: локальные Sentence-Transformers vs OpenAI Embeddings

### Скорость создания индекса

* **Локальные**: быстрые батч-инференсы на GPU; малые модели (384-768-d) кодируют быстро.
* **Облачные**: не требуют локального GPU, но ограничены сетевой латентностью/квотами.

### Качество поиска

* **Рекомендуемые локальные**:

  * Английский/универсально: `sentence-transformers/all-MiniLM-L6-v2` (384-d), `BAAI/bge-small-en-v1.5` (384-d).
  * Многоязычный (вкл. русский): `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, `intfloat/multilingual-e5-small`, либо `BAAI/bge-m3` (чуть тяжелее, но сильнее).
* **OpenAI text-embedding-3-small/-large**: высокая точность, предсказуемые расходы, минимум неопределенности с инфраструктурой.

### Стоимость владения и использования

* **Локальные**: «бесплатно за вызов» (кроме нашего железа).
* **Облачные**: дешёвый Opex за миллион токенов, удобно для масштабирования и метрик.

**Вывод по эмбеддингам**: стартуем локально (BGE-small или MiniLM-L6-v2); при переходе в облако/масштабировании сохраняем опцию OpenAI Embeddings для простоты.
> **Итоговый выбор (зафиксировано после пилота):** `intfloat/multilingual-e5-base` (768-d).
> **Почему:** (1) устойчивое качество на русском; (2) поддержка схемы `query:`/`passage:` (стандарт E5), что явно улучшило «именные» и определительные запросы в нашем корпусе; (3) накладные расходы приемлемы; (4) фактический прогон индекса показал корректные TOP-3 по sanity-чекам.
> **Альтернативы из shortlist:** `paraphrase-multilingual-MiniLM-L12-v2`, `multilingual-e5-small` — оставляем как fallback/эксперименты, но рабочий дефолт — **E5-base**.

## 3. Векторная БД: ChromaDB vs FAISS

### Скорость поиска и индексации

* **FAISS**: эталонная скорость, есть GPU-ускорение, множество индексов (Flat, IVF, PQ, HNSW). Легко ужимать память (PQ).
* **ChromaDB**: in-process стор с HNSW, очень удобен в Python-проекте; быстрый локально, но HNSW в памяти - внимательно к RAM.

### Сложность внедрения и поддержки

* **FAISS**: библиотека (не сервер) - минимум внешних сервисов; метаданные/фильтры - на нашей стороне/ORM.
* **ChromaDB**: коллекции, персистентность, фильтры «из коробки», дружелюбный DX; для больших нагрузок и HA лучше смотреть на специализированные движки (Qdrant/Milvus/Pinecone).

### Удобство в работе

* **FAISS**: идеален для MVP/прод-пайплайнов, когда важны скорость и контроль.
* **ChromaDB**: идеален для быстрых PoC в одном процессе; легко менять схему и итеративно «крутить» параметры.

### Стоимость владения (учёт инфраструктуры)

* Обе - опенсорс. FAISS позволяет гибко балансировать RAM/диск через IVF/PQ; Chroma проще «в быту», но требует больше памяти при росте.

**Вердикт**: для MVP в рамках этого задания берём **FAISS**. Для быстрых экспериментов в ноутбуке - Chroma; для прод-масштаба и кластера - Qdrant/Milvus/Pinecone.

## 4. Рекомендуемая конфигурация сервера

### Локальная разработка / малый трафик (MVP)

* **CPU**: 8-12 vCPU
* **RAM**: 32-64 ГБ
* **GPU**: современная GeForce RTX 50-series (Blackwell) или аналог
    - для INT4 8B: ориентир от ~6-8 ГБ VRAM (минимально), комфортнее 12-16 ГБ;
    - для FP16 8B: ориентир ~16 ГБ VRAM
* **Зачем**: 8B-LLM в INT4, быстрые локальные эмбеддинги, FAISS (CPU или GPU).

### Командный демо-стенд / десятки одновременных пользователей

* **CPU**: 16-24 vCPU; **RAM**: 64-128 ГБ; **GPU**: high-end потребительский 50-series или датацентровый с ≥24 ГБ VRAM (под длинный контекст, batch, реранкеры).

### Облачный гибрид без локального GPU

* **CPU**: 8-16 vCPU; **RAM**: 32-64 ГБ; **GPU**: нет
* Эмбеддинги локально/в облаке, поиск в FAISS, генерация через API (OpenAI). Хорошо, если политика допускает вызовы наружу (без передачи самих документов).

## 5. Архитектурные варианты

**A. Полностью локальный**

Эмбеддинги локально (BGE-small/MiniLM), **FAISS**, LLM - Llama 3.1-8B (INT4).

- (плюсы) Максимум приватности и контроля.
- (минусы) Требует GPU/DevOps, чуть ниже качество генерации.

**B. Гибрид (рекомендуемый)**

Эмбеддинги локально, **FAISS** on-prem; генерация - **OpenAI GPT-5** как сервис.

- (плюсы) Лучшее соотношение «качество/скорость/стоимость», простой масштаб.
- (минусы) Внешний вызов (проверить политику).

**C. Полностью облачный**

OpenAI Embeddings + векторный SaaS (Pinecone/Qdrant Cloud) + GPT-5.

- (плюсы) Мгновенный старт, мин. инфраструктуры
- (минусы) Opex и зависимость от внешних SLA.

**D. Python-PoC**

Эмбеддинги локально + **ChromaDB** in-process + Llama 3.1-8B.

- (плюсы) Максимально быстрые итерации в ноутбуке.
- (минусы) RAM-чувствительность, не для прод-нагрузки.

**Итоговый выбор для задачи**: **Вариант B (гибрид)**, с готовностью переключиться на A при строгой политике «без облака».

## Резюме

* **Векторная БД**: **FAISS** - как самый быстрый и простой старт для MVP; затем по мере роста - IVF-PQ/HNSW или переход в специализированный кластерный движок.
* **Эмбеддинги**: дефолт — `intfloat/multilingual-e5-base`; альтернативы для экспериментов — `paraphrase-multilingual-MiniLM-L12-v2`, `multilingual-e5-small`.
* **LLM**: локально `Llama-3.1-8B-Instruct` (INT4) + fallback на облако (GPT-5).
* **Инфраструктура**: для начала достаточно 8-12 vCPU, 32-64 ГБ RAM, GPU 12-16 ГБ VRAM.

# Задание 3. Создание векторного индекса базы знаний

## 1) Модель эмбеддингов

* **Название:** `intfloat/multilingual-e5-base` (768-мерные эмбеддинги).
* **Почему такой выбор:** устойчиво работает на русском, стандартные префиксы `query:` / `passage:` дают заметный прирост качества в поиске вопросов–ответов. (Семейство E5 — 768-мерные эмбеддинги; альтернативы — small/large и v2.)

## 2) Где код и как он устроен

* **Скрипт индексации:** `scripts/index/build_index.py`

  * Индексация **стриминговая**: чанки кодируются батчами и сразу добавляются в FAISS, метаданные пишутся в `kb_meta.jsonl`.
  * Вектор считается по строке вида: `passage: {title}\n\n{chunk}` (E5-best practice).

* **Скрипт поиска:** `scripts/index/search_index.py`

  * Запрос кодируется как: `query: {текст_вопроса}`.
  * Поиск — гибридный: FAISS (косинус через `IndexFlatIP` + L2-норма) → лёгкий лексический до-ранкер (токены/3-граммы/TF) → небольшой **title-boost**.

* **Проверка качества:** `scripts/index/quality_check.py` (валидируем, что правильный документ в TOP-3).

> Примечание про FAISS: для косинусной близости используется **L2-нормированные** векторы и `IndexFlatIP` (inner product). Это стандартный приём в FAISS.

## 3) База знаний и чанкование

* **База:** маскированные тексты (папка `knowledge_base`).
* **Чанкование:** по словам, ~**200** слов на чанк, overlap **40** слов (сохраняем `word_start/word_end`, путь, заголовок, id чанка и короткий `excerpt`).
* **Что реально получилось:** *30 файлов*, *207 чанков*; генерация индекса заняла **~51.13 сек**, запуск был на VM (8 vCPU / 16 GB). Отчет в `artifacts/kb_summary.json`. 

## 4) Как собрать и где лежит индекс

* **Индекс:** `artifacts/kb_faiss.index`
* **Метаданные:** `artifacts/kb_meta.jsonl`
* **Сводка:** `artifacts/kb_summary.json` (содержит модель, размерность, число чанков/файлов, время и параметры). 

Сборка (CPU, без GPU):

```bash
# зависимости
make deps3

# создать/пересоздать индекс (E5)
make kb.index
```

### 5) Пример запроса к индексу (поисковый запрос + найденные чанки)

```bash
# пример 1 — сущность
make kb.search Q="Кто такой Ноктиль-Мор?"

# пример 2 — «натуральный» вопрос без упоминания заголовка
make kb.search Q="тюрьма для волшебников где находится?"

# пример 3 — определение
make kb.search Q="Что такое Нордеверо?"
```

Вывод содержит TOP-K документов с путями и фрагментами текста. Поиск идёт **по смыслу полного текста чанка**, а не только по названию: заголовок даёт вспомогательный сигнал (title-boost) и повышает точность именных запросов, но ранжирование учитывает также лексическое совпадение и сами эмбеддинги текста.

Быстрый sanity-check (`make kb.qc`) прогоняет 4 тестовых вопроса и убеждается, что целевые статьи попадают в **TOP-3**. На текущей сборке — **все тесты проходят**.
